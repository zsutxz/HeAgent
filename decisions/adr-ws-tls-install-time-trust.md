# ADR-004 · WS TLS 信任锚 = 服务端身份公钥（安装期 pin）

> **状态**：accepted（2026-11-19 用户裁定「客户端不可能单独导入加密叶子证书，只有安装时信任服务器」）
> **来源**：Epic 73 立项批；需求真源 `docs/tls-connect-guide.md`「第二步」节（该页 gitignored，故决策正文落在本 ADR）
> **治理面**：WS 加密形态、证书签发与轮换、`heagent tls` 命令族、客户端信任契约

**Context.**
第一步（明文 `ws://` + 免 token）已交付（Epic 72）。第二步要做「`wss://` + Bearer token」，但客户端信任路径有三处硬约束：

1. 客户端按**整张叶子证书**匹配「导入记录」，而叶子证书默认 30 天到期 ⇒ 每台设备每 30 天重导一次；
2. 客户端「信任并锁定」的唯一入口是导入记录，现版本界面上建不起来 ⇒ 连「导一次长期用」都不成立；
3. 内网地址会变（DHCP、换网段、换网卡），证书 SAN 覆盖不住所有未来地址 ⇒ 主机名校验必然误伤。

同时服务端现状放大了问题：`scripts/gen_ws_cert.py::issue_leaf` 每次重签都 `genrsa -out key.pem`
**换新密钥**。因此哪怕客户端愿意做 pin，pin 也会每 30 天失效。

**Decision.**
信任锚改为**服务端身份公钥的 SPKI-SHA256**（不是叶子证书、不是 CA）：

- 服务端固定一对长期「身份密钥」`identity.key`；每次重签叶证书**复用它**（只换有效期与 SAN），
  故证书里的公钥恒定、pin 恒定。
- 客户端校验三条：① SPKI 命中 pin（允许 old/new 双 pin 并存）；② 证书未过期；③ **不校主机名**
  （身份由 pin 承担，地址漂移不再误伤）。
- 安装期信任三种交付形态，同一锚：
  - **A（默认）构建期内置 pin**：安装包资源里放一个 base64 pin，用户零操作；
  - **B 构建期内置 CA**：放 `ca.pem` 作 trust anchor（仍豁免主机名）；多服务端/多端点时用；
  - **C 安装向导一次性核对**：TOFU 记录 SPKI 并展示 `XXXX-XXXX-XXXX` 短指纹，与服务端控制台比对；
    用于「换服务端不重装」。
- 轮换：叶证书轮换**零客户端动作**；身份密钥轮换必须显式执行（`heagent tls rotate-key`）且用双 pin 过渡。
- CA 仍保留（签发与链形状标准），但**客户端不校链**——这是 pin 相比「内置 CA」的核心收益。
- 服务端实现范围收在 Epic 73 票树：身份密钥分离 → `heagent tls` 命令族 → 启动/`doctor` 自检 →
  `/api/status` 暴露指纹 → wss + token 落地与明文回收 → 文档与安全口径同步。

**Why.**
pin 把「每 30 天每台设备导一次证书」压成「安装包内置一个 32 字节值」，客户端改动面只有
「算 SPKI 哈希 + 比相等」，不需要证书链校验、不需要分发 `ca.pem`、不受证书轮换影响；主机名豁免则
把「内网地址一定会变」这个已知事实从「每次改地址都要重签并核 SAN」降级为「pin 保证身份，地址随便换」。
CA 方案在协议上并无优势，只在「一台安装包要认多台服务端」时才更省事——因此保留为形态 B 而非默认。

**Consequences / 风险（写进票面）.**

- pin 一旦泄露没有第二道约束（无域名、无链、无 CT 账本）⇒ pin 只随安装包分发，不进日志与截图。
- 身份密钥轮换是唯一需要人工介入的时刻；`rotate-key` 必须打印新 pin 并提示双 pin 过渡窗口，
  不得自动触发（否则等于每次重签都换密钥）。
- 叶证书到期、SAN 不含当前绑定地址是这套方案唯一会「静默失联」的两处 ⇒ 启动自检与 `doctor` 必须
  显性告警，不接受「握手失败才发现」。
- 需求真源 `docs/tls-connect-guide.md` 被 `.gitignore` 排除（客户端本地资料）⇒ 决策与判据以本 ADR
  与 Epic 73 票面为准，文档页只作客户端协作说明。
