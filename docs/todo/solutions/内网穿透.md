## 细化（六项）

### 1. 标题

把 `192.168.2.226:9201`（`external` 档 wss + Bearer token）经公网穿透发布，使非内网的收集端可提交
run、订阅事件、走项目通道。

### 2. 背景动机

- 服务端已是生产姿态（`.env`：`WS_HOST=192.168.2.226` + `WS_LAN_NO_AUTH=false` + `WS_TLS_*` 成对
  ⇒ `listener=external` / `tls=wss` / `auth=token`），但仅内网可达。
- HTTP 面默认只绑回环（`src/heagent/config/__init__.py:355`）且无认证 ⇒ 不能靠它对外。

### 3. 验收判据（简版；命令全文见 `## 验收判据`）

- 外部网络跑 `python scripts/ws_tls_attest.py --host <公网地址> --port <远端端口> --cert .heagent/tls/cert.pem`
  → 四段 `[OK]` / 退出码 `0`；加 `--token` 出 `101`；错 pin 回 `pin_mismatch`。
- 内网直连 `192.168.2.226:9201` 不回归。

### 4. 落点

- 部署面（不动 `src/`）：VPS `frps.toml` + 宿主 `frpc.toml`（`type="tcp"`，**`localIP` 必须写
  `192.168.2.226`**）；服务端配置零改动、无需重启。
- 方案正文：本文件 `## 方案`。

### 5. 规模

- S（≤ 半天）：VPS 装 frps 20 min + 宿主 frpc 20 min + 验收 30 min。

### 6. 风险与前置（简版；全文见 `## 风险与前置`）

- 前置：一台公网 VPS；能读到用户级 `~/.heagent/setting.md` 的 `WS_AUTH_TOKEN`。
- 只有 **TCP 透传**保 pin；HTTP/TLS 终结型隧道（cloudflared hostname / ngrok http / 反代）必 `pin_mismatch`。
- 别开 `WS_LAN_NO_AUTH`（公网等同裸奔，且与 `wss` 互斥）。

  ⇒ `listener=external` + `tls=wss` + `auth=token`，仅内网可达。

## 方案

### 路线对比（先选型，再落地）

| 路线 | 代表 | TLS 谁终结 | pin 是否仍有效 | 结论 |
| --- | --- | --- | --- | --- |
| A · TCP 透传 | frp `type=tcp` / ngrok `tcp` / `ssh -R` | 服务端（保持 `wss`） | **有效**（端到端） | **推荐** |
| B · 组网 | Tailscale / WireGuard / ZeroTier | 服务端 | **有效** | 收集端可控时最优（不暴露公网端口） |
| C · HTTP/TLS 终结 | cloudflared hostname / ngrok http / nginx 反代 | 隧道边缘（公网 CA） | **失效** ⇒ `pin_mismatch` | 不推荐（边缘证书轮换即反复失效） |

C 的退让形态：隧道内跑明文 `ws` 只靠 token，由边缘做 TLS —— 与「加密 + token 才是完整生产形态」的
既有口径冲突，仅在别无选择时采用，并显式记录风险。

### A · frp TCP 透传（推荐）

**① 公网 VPS（frps）**

```toml
# frps.toml
bindPort = 7000
auth.method = "token"
auth.token = "<强随机，且与 WS_AUTH_TOKEN 不同>"
allowPorts = [{ start = 19201, end = 19209 }]
```

- 防火墙放行 `7000/tcp` 与选定的远端端口（示例 `19201/tcp`）。
- 远端端口**避开 9201**（非标端口可压掉一部分扫描噪声）。

**② HeAgent 主机（frpc，Windows）**

```toml
# frpc.toml
serverAddr = "<VPS_IP>"
serverPort = 7000
auth.method = "token"
auth.token = "<同 frps>"

[[proxies]]
name = "heagent-wss"
type = "tcp"
localIP = "192.168.2.226"   # 必须是服务端实际绑定地址
localPort = 9201
remotePort = 19201
```

- ⚠️ `localIP` 不能写 `127.0.0.1`：非回环绑定后**回环腿刻意不存在**（`external` 档不注册回环监听），
  写回环会连不上。
- 注册为 Windows 服务（开机自启 + 断线自动重连），日志与 HeAgent 日志分开存放。

**③ 服务端配置：零改动**

- `WS_HOST` / `WS_PORT` / `WS_TLS_*` / `WS_AUTH_TOKEN` 全不动，**无需重启**（穿透只加一条外部通路）。

**④ 收集端：只改地址**

- `192.168.2.226:9201` → `<VPS_IP>:19201`。
- pin 与 token **原样照填**；域名/IP 不必进 SAN（客户端不校主机名）。

### 最轻量备选：`ssh -R`（VPS 不装 frp）

```bash
ssh -R 19201:192.168.2.226:9201 -N <user>@<VPS_IP>    # VPS 侧 sshd 需 GatewayPorts yes
```

- 优点：只依赖 sshd；缺点：无端口白名单、无常驻进程管理（需 systemd / Windows 计划任务守护）。

## 验收判据

全部从**外部网络**执行（手机热点或 VPS 上），逐条给命令与期望：

1. **四段承兑**（绑定面 / TLS 握手 / pin 对账 / 无 token 必须 403）：
   ```bash
   python scripts/ws_tls_attest.py --host <VPS_IP> --port 19201 --cert .heagent/tls/cert.pem
   ```
   期望：四段均 `[OK]`，退出码 `0`。
2. **认证正例**（追加第 ⑤ 段 101）：
   ```bash
   python scripts/ws_tls_attest.py --host <VPS_IP> --port 19201 --cert .heagent/tls/cert.pem \
     --token "<WS_AUTH_TOKEN 明文>"
   ```
   期望：出现 `101`，token 值不进任何输出。
3. **pin 逐字一致**：`heagent tls fingerprint --format pin` 的输出与内网直连时给客户端的内置值相同。
4. **端到端**：收集端收到 `hello`；提交一条 prompt 能收到 `event` 流并走到 `done`。
5. **反向判据**：无 token 必须 `403`；故意喂错 pin 必须回 `pin_mismatch`。
6. **不回归**：内网直连 `192.168.2.226:9201` 仍通（穿透是叠加，不是搬家）。

## 风险与前置

- **前置**：一台有公网 IP 的 VPS（或改走组网）；能读到用户级 `WS_AUTH_TOKEN`。
- **风险① pin 失效面**：只有 TCP 透传保端到端。C 路线边缘证书（Let's Encrypt 90 天轮换）会让内置 pin
  反复过期，客户端每次都要重新下发 ⇒ 不可运维。
- **风险② 免认证开关**：`WS_LAN_NO_AUTH=true` 是「同网段任何设备可驱使代理」，公网等同裸奔，且与 TLS
  互斥（`wss` + 该开关拒绝启动）。
- **风险③ 暴露面**：`WS_MAX_CONNECTIONS`（默认 16）与每项目在途上限会被占用；frp 与 WS 两套 token
  必须不同且强随机；建议 `allowPorts` 收窄 + 非标端口 + 失败登录告警。
- **风险④ 断线**：frpc 掉线即外部不可达；需自动重连与告警。服务端重启不影响 pin（`identity.key` 未换；
  `heagent tls rotate-key` 才会改，属唯一改 pin 动作）。
- **风险⑤ HTTP 面板**：若要发布 9101，须另加认证反代，且明确它不在安全边界内（可改项目配置）。

## 待用户裁决

- **穿透路线选哪条**：A · TCP 透传（推荐，pin/token 不变）／ B · 组网（不暴露公网端口，收集端需装客户端）／
  C · TLS 终结（要改 pin，证书轮换即反复失效）。对比表见 `## 方案`。
- **HTTP 面板是否也要发布**：默认 `127.0.0.1` 进不来；若要，须另加认证反代，且它不是安全边界。
