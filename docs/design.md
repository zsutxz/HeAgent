# HeAgent 设计说明

> 这份文档解释 HeAgent 想解决什么问题、刻意不解决什么问题，以及做设计取舍时遵循的原则。代码级实现细节见 [framework.md](framework.md)。

## 定位

HeAgent 是一个已在生产环境日常运行的单进程、异步 AI Agent 运行时。项目目标不是尽快堆出最多功能，而是把自主 Agent 的关键机制拆开、做清楚、做成可阅读的 Python 代码，便于理解、维护与按需扩展。

它重点覆盖以下主题：

- LLM Provider 适配与故障转移
- 工具注册与调用编排
- 长短期记忆与人格注入
- 子 Agent 角色化协作
- 运行时治理、审批和可观测性
- MCP 工具接入

## 面向对象

更适合以下读者或使用者：

- 想理解 Agent 内部执行链路的开发者
- 想基于现有框架继续扩展工具、Provider、策略层的人
- 想自托管部署、日常使用并按需改造运行时的人

## 设计动机

这个项目试图解决的不是“如何把所有 Agent 功能塞进一个仓库”，而是以下几类更基础的问题：

- 核心循环能否保持清晰，而不是被巨型类吞掉。
- Provider、工具、记忆、上下文、运行时治理能否解耦。
- 扩展新工具或新 Provider 时，能否尽量少改核心逻辑。
- 运行时状态、子任务和恢复点能否被结构化记录，而不是散落在消息里。

## 明确非目标

当前阶段不把下面这些内容当作项目承诺：

- 完整的 Web API 或多租户服务端产品
- 可直接上线的安全边界
- 浏览器自动化、语音、图像、多端 UI 等外围能力
- 一套统一而成熟的部署产品形态

尤其需要明确：

- `SafetyGuard` 不是沙箱。
- 外部 MCP server 不是受信执行环境。
- MCP 三原语（Tools / Resources / Prompts）已交付，但后续不再作为必要开发方向。

## 设计原则

- 可读性与可维护性优先于功能堆砌。
- 模块边界优先于临时方便。
- 默认使用声明式扩展点，而不是到处写特殊分支。
- 运行时状态尽量结构化、可恢复、可观测。
- 文档描述应以代码事实为准，避免把规划稿当成现状。

## 成功标准

如果这个项目的设计是成功的，应该满足：

- 新增工具或 Provider 时，不需要重写 `AgentLoop`。
- 阅读 `src/heagent/` 可以顺着模块边界理解系统。
- 一次运行的上下文、工具执行和子任务结果能被追踪。
- 用户可以从 `README` 上手，从 `framework.md` 理解实现。

## 当前成熟度

截至当前仓库状态，HeAgent 更准确的描述是：

- 一个可运行的 CLI / Python 库，含交互式聊天与 Textual TUI。
- 一个已在生产环境日常运行的项目；可阅读、可扩展仍是长期设计目标。

如果后续要演进到多租户服务产品、稳定 API 契约，再单独拆分新的设计文档更合适。
