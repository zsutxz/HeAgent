# Step 02 · brainstorm-options 报告

- 目标：`Goal-4`
- 执行角色：`bmad-brainstorming`（Creative Partner，headless 单轮子会话）
- 交互轮次：轮 0（开局）已产出，**待用户回复**

## 轮 0 · 复合问题

- **做什么**：把「远程 APK 经 WS 单通道驱动多个项目并行开发」从 ADR 冻结点落到一张可执行的实现路线 —— 提交帧加可选 `project_id`、远程只开四件事（列项目 / 提交 / 订阅 / 取消）、per-project 运行时与名额在远程面上同样成立。
- **为什么值得做**：现在能力不对称 —— 回环 HTTP 控制台（`POST /api/projects/{id}/runs`）项目编址完备，而唯一对外的 external 档 WS 帧只有 `prompt` 一个字段且 `extra="forbid"`，远程客户端手里有最强的认证链路、却指不了项目。
- **为什么现在值得做**：验收基线把「并行」写成硬判据（两项目**同时**各提交一 run、各自收完整事件流、取消其一、断线凭 cursor 续流不丢事件）——不是加个字段就完的小改，它同时压到帧模型、`network/` 依赖边界、并发名额归属与契约基线四处。
- **风险最高的不是功能，是边界**：`network/` 不得导入运行栈与 `config`（含 `pub.projects`）、`ws_server.py` 不得导入 `http_server.py` —— 项目编址的「知识」天生住在被禁的那一侧，落点选错会当场撞墙。
- **本轮不问「要不要做」**，只问「怎么切、先切哪刀、拿什么自证」。

## 轮 0 · 立场与技法

- **Creative Partner**：给主张不只提问，每条方向都有偏好与押注。
- **技法一 · Working Backwards（从真机验收倒推）**：把验收基线当成已上线事实，倒着问「哪一环没有可证性就会让这条基线假通过」——专门揪出「本地绿、真机不成立」的切分错误。
- **技法二 · Pre-mortem（失败预演）**：假设两周后 APK 侧报告「两项目串了 / 事件流断在取消处 / 连上了但列不出项目」，倒推成因，用它检验每个方向的失败面。
- **选择理由**：方向已被 ADR 冻结，发散空间只剩「实现切分与可证性」；这两个技法把发散压在还没决定的那一层。

## 轮 0 · 候选方向

### 方向 1 · 注入式项目目录端口（network 保持哑）
- **主张**：`network/` 只认一个由入口层注入的只读端口（`list_projects()`、`resolve(project_id) -> fenced root`），照抄 `__version__` 注入先例 —— 项目知识全留在 `cli/http.py` 装配侧。
- **风险**：注入面若返回 dict/对象容易反向污染帧形状；新装配契约漏注入会在 runtime 才炸，必须 fail-loud at load。
- **仍需的证据**：`cli/http.py::build_ws_servers` 现有注入清单能挂几个参数、`WsServerConfig` 是否已有承载位置；`tests/test_architecture_contracts.py` 里 network 边界的 exact 口径。

### 方向 2 · 帧转译成「内部服务调用」（WS 当第二张皮）
- **主张**：不在 WS 层重写项目解析，把提交帧转译成对既有 run 提交服务的调用，与回环 HTTP 面共用同一段项目编址 + 名额逻辑；服务对象下沉到 `http_protocol.py` 或入口注入。
- **风险**：容易滑成「为复用把 http_server 私有件搬出来」，把 `http_protocol.py` 撑成杂物间；两面错误码/语义被迫对齐，可能反向改动回环面既有行为。
- **仍需的证据**：`POST /api/projects/{id}/runs` 的编址 + 名额获取能否整段抽出而不带出 FastAPI/socket 依赖。

### 方向 3 · 契约快照先行（golden frames 钉死形状）
- **主张**：先落契约 —— 帧模型成功/失败样例、`transport_routes.json` 与 `transport_errors.json` 新基线条目、「旧客户端只发 `prompt` 仍工作」的兼容用例，全部先红后绿；实现跟测试形状走。
- **风险**：`extra="forbid"` 上加可选字段本身向后兼容，但失败错误码先钉死可能在开放问题 3/4 裁决前锁死语义，返工要重生成基线。
- **仍需的证据**：`scripts/contract_snapshot.py` 重生成后两份基线的实际 diff 规模。

### 方向 4 · 并发可证性先于功能（两项目并行的红测试倒驱动）
- **主张**：先写最难、最能证伪的测试 —— 两项目**同时**提交、`StubProvider` 拉长响应制造真重叠、断言事件流不串、名额独立且某项目打满不饿死另一个；测试红了再补实现。
- **风险**：per-project 名额若现在其实不存在（只有全局 slot 池），这条测试会把工作量暴露成「先造名额机制」；也可能反证 ADR 里「项目独立并发名额」是待建而非既有。
- **仍需的证据**：`engine/` 的 slot 池是按 project 键控还是全局单池 —— 决定方向 4 是「验收」还是「从零建」。

### 方向 5 · 只读投影最小暴露（安全面先收口）
- **主张**：远程面新造只读投影 DTO，帧里只出现 `project_id` + 展示名 + `available`，围栏根路径、配置细节、`session_id` 一律不出现；同时把「external + 非 docker 沙箱」的启动 WARNING 升成可观测态（`/api/status` 布尔）。
- **风险**：DTO 与内部模型多一层映射，`available` 判定口径会固化在这层；路径不外泄若只在序列化层做，容易在某条错误分支漏出。
- **仍需的证据**：既有回环面列项目返回值是否有路径/敏感字段；`/api/status` 的 `ListenerInfo` 扩字段是否算破坏性变更。

## 轮 1 · 裁决带来的位移

- 轮 0 的方向 1（注入口）原本假设「项目知识 = 磁盘上的仓库」；裁决把它换成**一张本机文件里的名单**——真正的问题从「怎么扫目录」变成「名单的性质是什么」。
- 名单本来是**本机便利设施**（`init --project` 的产物、CLI 切项目用），从未被设计成「暴露面白名单」；直接当远程命名空间，等于让一次本地动作静默产生网络后果。
- 「不可见刚 clone 未注册的仓库」是干净的一刀，但**启动工作区自身**通常就是未注册的临时 checkout ⇒ 命名空间里必然有一个「能提交但不出现在列表」的隐形成员需要交代。
- 名单可变（CLI 在服务运行期写入）、可残缺（手改、路径被删）、身份可能是路径派生 ⇒ `available` 与 `project_id` 的语义要重定义。
- 净效果：战场从**传输/帧**收缩到**注册表语义与一致性契约**——ADR-005 未覆盖、却决定客户端能否信任列表的那层。

## 轮 1 · 候选方向

### 方向 6 · 注册表是清单，暴露是另一层策略
- **主张**：区分「registered（本机资产清单）」与「remote-visible（网络可达集合）」；v1 可让两者恒等，但代码里留**一个命名清晰的投影函数**，作为未来加白名单/开关的唯一落点。
- **风险**：投影若只做透传会被当冗余抽象内联掉；反过来真加开关又变成「默认暴露、需手动关」。
- **仍需的证据**：注册条目真实字段与落点、是否存在「敏感但不该暴露」的典型条目、启动时是否已有暴露面播报先例（`ws event=exposed`）。

### 方向 7 · `available` 从「目录存在」改为「可被远程提交」的判定
- **主张**：`available` 应是**每次列项目时现场计算**的谓词（工作区根可读 + 具备项目配置 + 未被隔离），可能在列与提交之间翻转。
- **风险**：布尔值丢诊断信息；若把 `available=false` 的条目从列表过滤掉，就变成「静默隐藏」。
- **仍需的证据**：今天「注册了但用不了」的可观测失败有哪几种，提交侧现有错误码能否复用为 `available` 的理由字段。

### 方向 8 · 未注册目录一律隐藏；但启动工作区要不要「隐式成员」
- **主张**：未注册即「不是项目」。岔路在启动工作区：提交帧缺省 `project_id` 时落到它身上。(a) 恒为隐式零号成员；(b) 仅当启动工作区已注册才生效，否则拒绝并指向清单。
- **风险**：(a) 与「真源 = 已注册条目」字面冲突，且把启动路径的目录名泄给远程；(b) 让「直接 `heagent http-server` 起在随便一个仓库」这个最常见姿势在远程面完全不可用。
- **仍需的证据**：未注册启动工作区的实际占比；`project_id` 缺省分支能否拿到启动工作区身份。

### 方向 9 · 名单读写的时效契约（缓存 vs 每请求读）
- **主张**：远程列表是对运行期可变文件的投影，须显式定契约：每请求读取解析（弱一致、永远最新）或按 mtime 缓存；并明确「已移除条目的旧 run 继续存在」是预期。
- **风险**：每请求同步文件读违反「库代码无同步 I/O」；缓存 TTL 会让「刚注册完看不到」被当故障；名单半截写（非原子）时列表 500 或静默少几条。
- **仍需的证据**：读路径是否已有 async/缓存封装、写入是否原子、条目数量级、一次解析耗时。

### 方向 10 · `project_id` 必须是注册表内部的不可变代理键
- **主张**：远程客户端会**记住** `project_id`（重连、订阅、取消），故必须与显示名、路径、slug 解耦：entry 存不可变代理键，`name` 可变，路径绝不下发。
- **风险**：现有条目可能没有代理键（或键是 path-derived）⇒ 需用户级迁移，且不能打破旧条目；手改过名单的用户可能造出重复或缺键条目。
- **仍需的证据**：当前条目身份字段是什么（是否 path-derived、是否唯一）、名单是否鼓励手改、`project_id` 是否已在别处契约中定义。

## 收敛轮（轮数用尽后的自动收敛）

### 收敛短名单（按优先级）

1. **帧转译成内部服务调用（WS 当第二张皮）** —— 采纳：提交 run 的服务已在 HTTP 面，WS 只应是同一服务的第二入口，否则「四件事」会长出两套语义 · 风险：抽象层过薄时沦为 pass-through，日后两面各自加字段而契约分叉 · 仍需证据：HTTP 提交 run 的入口函数边界能否被入口层直接复用。
2. **注入式项目目录端口** —— 采纳：这是方向 1/2 的唯一合规形态（`network/` 不得 import `config` / `pub.projects`）· 风险：端口方法随需求漂移成注册表远端代理 · 仍需证据：端口要不要「已注册但目录不存在」的三态返回。
3. **清单与暴露面分离（投影函数）** —— 采纳：裁决「列表真源 = 注册表」需要单一可测函数承载 · 风险：投影里塞进可用性/权限判断后成隐藏策略点 · 仍需证据：远程集合是否含 `default` 项（需显性裁决）。
4. **`project_id` 不可变代理键** —— 采纳（分阶段）：path-derived 键在目录移动后失效 · 风险：换键要迁移注册表文件，与 `register()` 按 `normcase(path)` 去重冲突 · 仍需证据：远程契约是否允许跨会话持久化 `project_id`。
5. **并发可证性先于功能** —— 采纳：本次唯一新增失败面是多项目并发提交的共享状态 · 风险：红测试过早锁死实现细节或倒逼多余全局锁 · 仍需证据：单项目内并发冲突是否完全沿用既有 `run_conflict`。
6. **契约快照先行** —— 采纳（收窄）：只对 WS 帧信封与「四端点白名单」落 golden，业务 payload 不钉 · 风险：信封一改就双份维护 · 仍需证据：golden 落点是新增第五份基线还是并入 `transport_routes.json`。
7. **名单时效契约** —— 采纳（轻量档）：注册表 ≤32 项，每请求读、不加 mtime 缓存 · 风险：`list()` 每条一次 `is_dir()`（≤31 次同步 stat 在事件循环上）· 仍需证据：gap（远程列项目 P95 延迟预算未定）。

### 被实测证据消解的条目

- **方向 8（隐式成员）**：`_default_entry()` 已返回 `id="default"` / `is_default=True` / `path` = 启动工作区 / `available` 现场计算，`list()` 无条件拼进结果 ⇒ 启动工作区**本来就是零号成员**，只剩「远程投影是否包含它」这一个裁决点。
- **方向 7（`available` 重定义）**：`available` 已由 `list()` / `find()` 用 `Path(path).is_dir()` 现场计算（docstring 明写 `Availability is computed when listing.`）⇒ 不需新谓词字段；「可被远程提交」= `available` ∧ 沙箱档提示，属展示层派生。
- **方向 5（只读投影最小暴露）**：`ProjectEntry` 已 `frozen` + `extra="forbid"` 且有界 ⇒ 只剩一个动作：投影时剔除 `path` / `last_opened_at`。降级为方向 6 的实现细节。

### 交给 Step 03 的主线验收条款

- **A. 架构边界零新增**：`network/` 不得 import `heagent.config` / `heagent.pub.projects` / `heagent.engine` / `heagent.agent`。判据：`pytest tests/test_architecture_contracts.py -q` 绿 + grep 输出为空。
- **B. `project_id` 缺省语义唯一且不回落**：缺省 ⇒ 启动工作区；显式 id 未登记 ⇒ 显性错误；已登记但目录不存在 ⇒ 显性错误。禁止任何一条回落为 `default`。
- **C. 远程可见集合 == 注册表投影**：固定夹具（default + 3 项）下逐项相等，字段只含 `project_id` / `name` / `available`，`path` 不得出现；实现内不得出现目录扫描。
- **D. 并发不串味**：两项目同时提交，归属正确、事件流互不投递；同项目冲突沿用既有冲突语义与错误码。
- **E. 四件事白名单不扩张**：远程可提交帧/端点恒为 {列项目, 提交 run, 订阅事件流, 取消 run}；守卫测试断言第五个提交类帧进不来；golden 信封快照断言无 `project_id` 字段。

### 遗留缺口

- **path-derived id 稳定性**：`project_id_for()` = `"p" + sha256(normcase(path))[:8]`，目录移动/重命名即换键；`default` 的 id 是字面量（不在哈希空间）⇒ 两套 id 形态并存，远程契约不能假设 id 格式统一或跨会话可缓存。
- **`list()` 文档/实现不一致（实测）**：docstring 写「`default` 恒在首位」，实现 `return [*registered, entries[0]]` 把 default 放**末位** ⇒ 若把顺序写进契约或 golden，必须先裁决「顺序是否承诺」。
- **注册表不可读时静默降级**：`load()` 对 OSError/UnicodeError 只 `logger.warning` 并返回空表 ⇒ 远程列表退化为只剩 `default`，与「未注册一律隐藏」在客户端不可区分。
- **`available` 的 TOCTOU**：`available` 是列表采样时刻的 `is_dir()` 结果，提交时才真正使用 ⇒ 采样与提交之间目录消失的行为（拒收 vs 运行期失败）尚无契约。
