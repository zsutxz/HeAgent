# release-notes

## Pattern
发布说明|发布公告|release notes|CHANGELOG|升级注意|本周期改动汇总

## Steps
1. **归类**：按「新增能力 / 行为变更 / 修复 / 破坏性变更」四栏分组；无法归类的先放一边，不硬塞。
2. **换视角**：把「重构了 X」「重命名了 Y」改写成「现在可以……」「不再需要……」；纯内部重构若不改变外部行为，不进发布说明。
3. **标影响面**：每条注明受影响对象（CLI 命令 / HTTP 端点 / 配置键 / 库 API）。
4. **写升级注意**：破坏性变更必须给「旧写法 → 新写法」对照，并说明不迁移的后果。
5. **收尾自检**：逐条确认「使用者读到这条能做什么」；只描述事实而说不出动作的，重写或删掉。

## 输出格式

```markdown
## 破坏性变更
- `<旧命令>` 改名为 `<新命令>`。旧名不再注册，直接输入会被当作普通 prompt 处理。

## 新增
- 支持 `<能力>`：`<一行可执行命令>`

## 修复
- 修复 `<场景>` 下的 `<症状>`；升级后无需再做 `<旧绕过手段>`。
```

## 资源

`scripts/group_commits.py` 是可选辅助脚本：把 `git log --oneline` 按前缀粗分组，减少手工归类时间。
它不是发布流程的一部分，只在改动量大时用。

```bash
# 相对路径按技能包根解析（先 cd 到本包目录，或改写成完整路径）
git log --oneline v0.9.0..HEAD | python examples/skill-package/release-notes/scripts/group_commits.py
```

## 不要做

- 不要把提交信息原样搬进发布说明（提交信息写给维护者，发布说明写给使用者）。
- 不要统计「改了多少行 / 多少文件」——那不是使用者关心的信息。
