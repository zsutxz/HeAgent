# HeAgent 项目改进需求文档 (PRD)

## 一、文档概述

**项目名称：** HeAgent 项目改进计划  
**文档版本：** 1.0  
**创建日期：** 2026-11-11  
**文档状态：** 草稿  
**来源文档：** `_bmad-output/planning-artifacts/project-improvement-report.md`

**项目背景：**
HeAgent 是一个架构清晰、文档完善的实验性 AI Agent 框架（v0.8.4）。经过系统性审查，项目在架构设计、测试覆盖、文档完整性方面表现优秀，但在大文件重构、用户体验、性能优化、工程自动化等方面存在改进空间。

**项目目标：**
- 提升代码可维护性（降低 30% 单文件复杂度）
- 优化用户体验（降低 50% 配置错误率）
- 提升开发效率（增加 40% CI 自动化覆盖）
- 增强系统性能（缓存与批量操作优化）

---

## 二、功能需求 (Functional Requirements)

### FR1：大文件重构
**描述：** 拆分超过 800 行的大文件，降低单文件复杂度，提升可维护性。

**子需求：**
- FR1.1：拆分 `network/http_server.py`（1,965 行）为 `routes/`、`handlers/`、`middleware/` 模块
- FR1.2：拆分 `cli/goal.py`（1,636 行）为 `goal/cli_commands.py` + `goal/cli_display.py`
- FR1.3：拆分 `engine/workflow_runner.py`（1,346 行），提取状态机逻辑到独立模块
- FR1.4：拆分 `config/catalog.py`（1,350 行）为 `catalog/schema.py` + `catalog/validator.py`

**验收标准：**
- 所有拆分后的单文件行数 < 1,000 行
- 保持原有功能不变，所有测试通过
- 架构契约测试 `tests/test_architecture_contracts.py` 更新并通过

**优先级：** 高（1-3 个月内完成）

---

### FR2：异常体系完善
**描述：** 建立完整的异常层次结构，为每个模块定义专用异常，统一错误码体系。

**子需求：**
- FR2.1：为核心模块定义专用异常（`ProviderException`、`ToolException`、`EngineException` 等）
- FR2.2：建立异常层次结构（基类 → 分类 → 具体异常）
- FR2.3：设计并实现统一错误码体系

**验收标准：**
- 每个核心模块（provider/tool/engine/agent）至少有 3 个专用异常
- 所有异常继承自统一基类
- 错误码文档完整，包含错误码 → 异常类型 → 处理建议的映射

**优先级：** 中（3-6 个月内完成）

---

### FR3：代码复杂度降低
**描述：** 提取重复逻辑，简化深层嵌套，消除魔法数字。

**子需求：**
- FR3.1：提取 `cli/http_console.py` 与 `cli/interactive.py` 的会话管理共享逻辑
- FR3.2：重构 `goal/application.py` 的多层条件嵌套，使用策略模式或责任链模式
- FR3.3：消除代码中的魔法数字，定义为具名常量

**验收标准：**
- 会话管理逻辑抽象为共享基类或工具函数
- `goal/application.py` 最大嵌套深度 ≤ 3 层
- 代码中无裸数字（除 0/1/-1），所有配置值定义为常量

**优先级：** 中（3-6 个月内完成）

---

### FR4：性能优化
**描述：** 引入缓存机制、批量操作优化、懒加载，提升系统性能。

**子需求：**
- FR4.1：实现 Provider 元数据缓存（`@lru_cache`）
- FR4.2：实现技能匹配结果缓存
- FR4.3：优化技能匹配为批量预计算
- FR4.4：实现技能包按需懒加载
- FR4.5：延迟导入大型依赖（如 anthropic、openai SDK）

**验收标准：**
- Provider 元数据缓存命中率 > 80%
- 技能匹配性能提升 > 30%（基准测试对比）
- 冷启动时间降低 > 20%

**优先级：** 中（3-6 个月内完成）

## 三、非功能需求 (Non-Functional Requirements)

### NFR1：代码质量
**描述：** 保持高代码质量，严格遵循 PEP 8，类型注解完整。

**指标：**
- 测试覆盖率 ≥ 87%
- ruff lint 零错误
- mypy 类型检查零错误
- 所有公开 API 有类型注解

---

### NFR2：性能
**描述：** 保证系统性能，控制资源消耗。

**指标：**
- 冷启动时间 < 2 秒
- Provider 调用延迟 < 100ms（不含 LLM 调用时间）
- 工具并行执行效率 > 90%
- 内存占用 < 500MB（空闲状态）

---

### NFR3：可维护性
**描述：** 代码易于理解和维护。

**指标：**
- 单文件最大行数 < 1,000 行
- 函数最大行数 < 50 行
- 圈复杂度 < 10
- 所有模块有详细 docstring

---

### NFR4：可扩展性
**描述：** 系统易于扩展，支持插件机制。

**指标：**
- 新增 Provider 无需修改核心代码
- 新增 Tool 通过 `@tool` 装饰器即可注册
- MCP 协议完整支持

---

### NFR5：安全性
**描述：** 系统安全可靠，数据不泄露。

**指标：**
- 无已知高危漏洞

- 沙箱隔离有效

### NFR6：兼容性
**描述：** 支持主流平台和 Python 版本。

**指标：**
- 支持 Python 3.11+

---

### NFR7：文档完整性
**描述：** 文档完整、准确、易懂。

**指标：**
- 所有公开 API 有文档

## 四、技术约束

### 架构约束
- 必须保持严格的 DAG 依赖关系
- `network/` 模块不得导入运行栈
- 模块间数据传递必须使用 Pydantic 模型

### 测试约束
- 所有代码改动必须有对应测试
- 架构契约测试 `tests/test_architecture_contracts.py` 必须通过
- 测试覆盖率不得低于 87%

### 性能约束
- 大文件重构不得降低性能 > 5%
- 性能优化必须有基准测试对比

### 安全约束
- 不得削弱现有安全机制
- 新增功能必须经过安全审查

## 七、风险与依赖

### 风险

1. **大文件重构风险**
   - 风险：可能引入回归 bug
   - 缓解：增强测试覆盖，使用 `scripts/verify_baseline.py` 验证基线

2. **性能优化风险**
   - 风险：缓存策略不当可能导致数据不一致
   - 缓解：建立性能基准测试，验证缓存一致性

3. **CI/CD 建设风险**
   - 风险：自动发布可能误发布不稳定版本
   - 缓解：建立多阶段发布流程（dev → beta → stable）

### 依赖

1. **外部依赖**
   - GitHub Actions（CI/CD）
   - PyPI（发布）
   - Read the Docs 或 GitHub Pages（文档托管）

2. **内部依赖**
   - 现有测试框架（pytest）
   - 现有质量门禁（`scripts/quality_gate.py`）
   - 现有架构契约测试
