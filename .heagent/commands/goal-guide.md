# /goal-guide —— 该不该开 goal 工作流

用户叫你不要动手，只做判定与指路。**你自己不执行任何 `/goal` 子命令**，也不要伪造执行结果——斜杠命令只能由用户敲。工作流契约（步骤顺序、输入输出、门禁）的唯一权威是 `.heagent/skills/he-goal/workflow.md`，不要凭记忆复述它。

## 第一步：判定

先问清目标，再按下表给结论。**默认倾向是「不启动」**——误开工作流要跑八步、产出整套目录，成本远高于漏判。

| 情形 | 结论 | 理由 |
|------|------|------|
| 改一处代码 / 修一个 bug / 加一个小功能 | 直接做 | 一次会话能收口，开工作流是负担 |
| 问一个问题 / 查一段代码 / 做一次探查 | 直接答 | 没有交付物，`_he-output/goals/<id>/` 只会留垃圾 |
| 从零做一个项目、需求到交付、跨多阶段 | 启动工作流 | 正是 `/goal` 的设计目标 |
| 已经开了 goal 的工作 | 续跑 | 别再开新 goal |
| 只是「想理清思路 / 讨论方案」 | 先讨论 | 需求没定就开，第一步市场调研会问一堆你还没想清的事 |

**判断口径**：这个目标是否需要多个阶段、需要中途停下来等你决策、并且产出要落盘可追溯？三条都满足才值得开。

## 第二步：指路

判定要开之后，只给命令，按用户当前状态选一条：

- 新目标 → `/goal new <目标描述>`
- 一次推进一步（每步可停可看） → `/goal next`
- 连续推进到下一个断点 → `/goal run`
- 想看进度 / 已经跑到哪了 → `/goal status`
- 步骤停在等你回答 → `/goal resume <回复>`（回答会写进需求文档的「用户补充」段）
- 想先停一停 → `/goal pause`
- 想无人值守定时推进 → `/goal auto [cron]`

用户问「还有别的做法吗」时，可以提 `/goal run`（一次推多步）与 `/goal auto`（挂定时）的差别：前者由你守着，后者交给 cron。

## 第三步：别做的事

- **不要手改**需求文档（新 goal 为 `brief.md`，存量 goal 沿用 `require.md` / `GOAL.md`）的「原始需求」段，也不要改 `epics.md` 里已冻结的验收标准——那是用户的输入，改了就丢了溯源。
- **不要用 `skill_delete` / `skill_archive` 动 `he-goal` 包**——它同时承载运行时契约（`workflow.md` + `templates/`），删掉 `/goal` 会直接报错。
- **不要替用户执行**。用户问「帮我跑一下」时，把命令写给他，说明 agent 没有这个权限。
- 中断不会丢进度（checkpoint 在盘）。用户担心白跑一趟时，直接让他续跑。
